Research date: 2026-11-06. Every version, license and feature claim below was checked against a primary source (repo LICENSE file, README, official docs) fetched on that date; the URL is given next to each claim. Where a page did not state something, it is marked **not documented / unverified** rather than inferred.

## Part A. MCP specification status (as of 2026-11-06)

### Current revision: `2026-07-28`
- The versioning page states: "The **current** protocol version is **2026-07-28**" and that `2025-11-25` and earlier are the "handshake-based protocol revisions". https://modelcontextprotocol.io/specification/versioning
- Key changes vs 2025-11-25 (changelog, https://modelcontextprotocol.io/specification/2026-07-28/changelog):
  - Protocol-level sessions and the `Mcp-Session-Id` header removed; `initialize` handshake removed; every request carries `_meta["io.modelcontextprotocol/protocolVersion"]` and client capabilities (SEP-2567, SEP-2575).
  - New mandatory `server/discover` RPC.
  - `subscriptions/listen` replaces the HTTP GET stream and `resources/subscribe`.
  - **Multi Round-Trip Requests (MRTR)** replace server-initiated requests: servers return `InputRequiredResult` (`resultType: "input_required"`) carrying `inputRequests` (elicitation/sampling/roots), client retries with `inputResponses` + opaque `requestState` (SEP-2322). https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr
  - Tasks moved out of core into the official extension `io.modelcontextprotocol/tasks` (SEP-2663).
  - Roots, Sampling and Logging deprecated (SEP-2577); HTTP+SSE transport formally Deprecated (SEP-2596); Dynamic Client Registration deprecated (PR #2858).
  - OpenTelemetry trace-context propagation documented for `_meta` keys `traceparent`, `tracestate`, `baggage` (SEP-414); `Mcp-Method` / `Mcp-Name` headers required on Streamable HTTP POSTs so intermediaries can route without parsing bodies (SEP-2243); `ttlMs` / `cacheScope` on list results (SEP-2549).

### Authorization section (https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
Normative requirements, quoted:
- Roles: "A protected MCP server acts as an OAuth 2.1 resource server"; "An MCP client acts as an OAuth 2.1 client"; the authorization server "may be hosted with the resource server or a separate entity."
- "Authorization servers **MUST** implement OAuth 2.1" (draft-ietf-oauth-v2-1-13).
- "MCP servers **MUST** implement OAuth 2.0 Protected Resource Metadata (RFC9728). MCP clients **MUST** use OAuth 2.0 Protected Resource Metadata for authorization server discovery."
- "MCP authorization servers **MUST** provide at least one of" RFC 8414 metadata or OpenID Connect Discovery; "MCP clients **MUST** support both discovery mechanisms".
- "MCP clients **MUST** implement Resource Indicators for OAuth 2.0 as defined in RFC 8707"; the `resource` parameter "**MUST** be included in both authorization requests and token requests" using the canonical server URI. "MCP servers **MUST** validate that access tokens were issued specifically for them as the intended audience".
- Token passthrough prohibited: "MCP servers **MUST NOT** accept or transit any other tokens"; "MCP clients **MUST NOT** send tokens to the MCP server other than ones issued by the MCP server's authorization server."
- RFC 9207 issuer identification: AS "**SHOULD** include the `iss` parameter"; clients "**MUST** apply the validation" when present (SEP-2468).
- Scope challenges: 401/403 with `WWW-Authenticate: Bearer ... scope=...`, step-up flow defined.

Client registration (https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration):
- Three mechanisms with a stated priority: pre-registered credentials → **Client ID Metadata Documents** (CIMD, `draft-ietf-oauth-client-id-metadata-document-00`; "Authorization servers and MCP clients **SHOULD** support") → Dynamic Client Registration (RFC 7591, "**MAY** support"; "Dynamic Client Registration is deprecated... retained for backwards compatibility") → prompt the user.
- AS advertises CIMD via `client_id_metadata_document_supported: true`. Client credentials must be keyed by AS `issuer` (SEP-2352).

Authorization extensions (https://modelcontextprotocol.io/docs/extensions/overview and https://github.com/modelcontextprotocol/ext-auth):
- Extensions are formal since 2026-07-28 (`extensions` field in capabilities; lifecycle Experimental → Beta → Stable, SEP-3392).
- **Enterprise-Managed Authorization** (`io.modelcontextprotocol/enterprise-managed-authorization`) — **Stable**, revision `specification/stable/enterprise-managed-authorization/2026-07-28/`. It is the Cross-App-Access model: client logs in to the enterprise IdP, exchanges the ID token for an **ID-JAG** ("Identity Assertion JWT Authorization Grant"), then exchanges the ID-JAG at the MCP server's AS for an access token. The docs page states: "The IETF OAuth working group defines ID-JAG in draft-ietf-oauth-identity-assertion-authz-grant" (the successor of draft-parecki-oauth-identity-assertion-authz-grant) and that it originated as SEP-990. Vendor support table lists Okta (XAA), Ping, Descope, Auth0 (early access), Keycloak ("Experimental... since 26.7.0 behind the `identity-assertion-jwt` feature flag"), Athenz, Janssen, ThunderID, Stytch, WorkOS, Scalekit, plus Cloudflare workers-oauth-provider and FastMCP 4.0 as server frameworks. https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization
- **OAuth Client Credentials** (`io.modelcontextprotocol/oauth-client-credentials`) — Stable, for machine-to-machine.
- Other official extensions: MCP Apps (Stable), MCP Tasks (Beta, destination Core), Skills over MCP (Beta), Server Cards (Beta). An **experimental "interceptors" extension** (SEP-2624, `modelcontextprotocol/experimental-ext-interceptors`, Interceptors Working Group) is "for prototyping and feedback only, and is not an accepted or official MCP extension" — relevant as a possible future standard for gateway pre/post hooks. https://github.com/modelcontextprotocol/experimental-ext-interceptors

### Human-in-the-loop approval primitives
- There is **no dedicated "approval" request type**. Two official mechanisms cover it:
  1. **Elicitation** (core; https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation): server returns `InputRequiredResult` containing `elicitation/create` in `form` mode (flat JSON-schema form; three-action model `accept` / `decline` / `cancel`) or `url` mode (out-of-band, for secrets/OAuth/payment). Spec: "Clients **SHOULD** implement user approval controls"; servers "**MUST NOT** use form mode elicitation to request sensitive information".
  2. **Tasks extension** (`io.modelcontextprotocol/tasks`, Beta → Core; https://modelcontextprotocol.io/extensions/tasks/overview): statuses `working`, `input_required`, `completed`, `failed`, `cancelled`; methods `tasks/get`, `tasks/update`, `tasks/cancel` (the blocking `tasks/result` and `tasks/list` were removed). Explicitly intended for "Human-in-the-loop workflows. Approval gates, review steps, or any operation that pauses for user confirmation. The task moves to `input_required` and the client presents the request."
- Tool annotations (`readOnlyHint`, `destructiveHint`) remain available to gateways for approval policy (ToolHive's Cedar context exposes them; see below).

### 1. agentic-community/mcp-gateway-registry ("MCP Gateway & Registry")
- **License:** Apache-2.0 — LICENSE file begins "Apache License Version 2.0, January 2004" (https://raw.githubusercontent.com/agentic-community/mcp-gateway-registry/main/LICENSE). No paid tier found.
- **Language/governance/maturity:** Python (`pyproject.toml` present). Hosted by the "Agentic Community" GitHub org; the predecessor repo `aarora79/mcp-gateway` (a personal repo) is archived with a note that the project "has moved to github.com/agentic-community/mcp-gateway-registry" (https://raw.githubusercontent.com/aarora79/mcp-gateway/main/README.md). An AWS Open Source Blog post describes it and its federation with Amazon Bedrock AgentCore (https://aws.amazon.com/blogs/opensource/governing-ai-assets-at-scale-with-mcp-gateway-and-registry/). **I could not verify it was ever under the `awslabs` org.** ~1.0k stars. Latest release 1.36.0 (2026-11-03); seven releases between 2026-09-09 and 2026-11-03, i.e. roughly weekly (https://github.com/agentic-community/mcp-gateway-registry/releases).
- **Transports:** Registered servers must "expose an MCP-compatible endpoint (typically `/mcp` for Streamable HTTP)" reachable over the network (docs/faq/deploying-and-registering-servers-agents.md). SSE and stdio hosting are not documented; it does not run servers.
- **Authentication:** NGINX `auth_request` → auth-server `/validate`. `AUTH_PROVIDER` selects Keycloak (default) or Microsoft Entra ID; README additionally lists Okta, Auth0, Cognito, PingFederate. IdP tokens are RS256 validated against JWKS; self-signed gateway tokens are HS256. Programmatic clients send a bearer token in the `X-Authorization` header; browser users get a session cookie. No RFC 9728 / DCR / CIMD support for inbound MCP clients is documented (docs/auth.md: "The page does not mention the MCP spec's OAuth 2.1 profile"). Egress: stored static credentials (Fernet-encrypted), gateway-minted `client_credentials`, per-user consent via `/oauth2/egress/connect` (`EGRESS_AUTH_ENABLED`), and `obo_exchange` (Entra only, "an app-only token minted as the gateway itself"); the README's 1.35.0 highlight claims "Keycloak RFC 8693 token exchange for OBO" shipped, but docs/auth.md does not describe it — **treat RFC 8693 support as unverified**. The client's gateway token "is never forwarded to the upstream MCP server". https://raw.githubusercontent.com/agentic-community/mcp-gateway-registry/main/docs/auth.md
- **Authorization:** Scope documents in the `mcp_scopes` Mongo/DocumentDB collection (`scope_name`, `server_access[].{server,methods,tools}`, `group_mappings`, `custom_scopes`); default-deny, first match wins; `validate_server_tool_access()` in `auth_server/server.py`. Virtual servers add `required_scopes` and `tool_scope_overrides` with `tool_alias`. **No OPA/Cedar/ext_authz hook and no runtime pre/post tool-call hook.** The only hooks are a fail-closed *registration gate* (HTTP 200 allow / 403 deny; "Fail-closed: blocks registration if gate is unavailable") and fire-and-forget notification webhooks (`X-Registry-Signature` HMAC). https://raw.githubusercontent.com/agentic-community/mcp-gateway-registry/main/docs/scopes.md and .../docs/registration-webhooks.md
- **Guardrails:** none at runtime. Registration-time scanning uses Cisco AI Defense MCP Scanner / A2A Scanner / Skill Scanner (`SECURITY_SCAN_ENABLED`, `SECURITY_SCAN_ON_REGISTRATION`, `SECURITY_BLOCK_UNSAFE_SERVERS`, `SECURITY_ANALYZERS=yara`; the LLM analyzer "needs the LiteLLM library, which the registry no longer installs"). No rug-pull / description-drift detection. https://raw.githubusercontent.com/agentic-community/mcp-gateway-registry/main/docs/security-scanner.md
- **Observability:** OpenTelemetry SDK; when an OTLP endpoint is configured it "pushes metrics + traces via OTLP"; auto-instrumentation gives per-route spans; tool metrics `mcpgw_registry_tool_invocations_total`, `tool_execution_duration_milliseconds`; Prometheus on :9464; Grafana in Compose/ECS. Span attributes for tool arguments are not documented. Audit logging with credential masking is advertised in the README (docs/audit-logging.md). https://raw.githubusercontent.com/agentic-community/mcp-gateway-registry/main/docs/OBSERVABILITY.md
- **Deployment:** Helm charts (auth-server, registry, keycloak-configure, mongodb-configure, bundled "stack") for EKS; Terraform for ECS; Docker Compose for EC2. No operator/CRD. Adding a server = UI "Register" form, `api/registry_management.py register --config <json>`, or REST API (`/openapi.json`). https://raw.githubusercontent.com/agentic-community/mcp-gateway-registry/main/charts/README.md
- **Tool scoping:** virtual MCP servers aggregating tools with per-tool access and aliases; semantic + lexical tool search (OpenAI/Azure/Bedrock embeddings).
- **A2A:** yes — since 1.27.0 each enabled agent gets authenticated `/agent/{path}` routes, `invoke_agent` grant, gateway-aware agent-card discovery; "agent-to-agent traffic runs peer-to-peer" by default. https://raw.githubusercontent.com/agentic-community/mcp-gateway-registry/main/docs/release-notes/1.27.0.md
- **Admin UI / health:** web UI with server status (green/red/gray), manual refresh, `/health` endpoints.

### 2. IBM/mcp-context-forge (ContextForge)
- **License:** Apache-2.0 (LICENSE verified). No paid tier.
- **Language/governance/maturity:** Python (`pyproject.toml`). IBM-maintained single-vendor project. ~4.8k stars. Latest v1.1.0 (2026-10-20); ten releases from v1.0.4 (2026-06-23) to v1.1.0, about every 13 days. https://github.com/IBM/mcp-context-forge/releases
- **Transports:** "Transport over HTTP, JSON-RPC, WebSocket, SSE (with configurable keepalive), and Streamable HTTP" (README). stdio servers are bridged with the separate `mcpgateway.translate` process: `--stdio "uvx mcp-server-git" --expose-streamable-http --port 8000` (also `--expose-sse`, `--stateless`, `--jsonResponse`); the docs give a Dockerfile recipe with a `/healthz` HEALTHCHECK. It is a sidecar you build, not automatic wrapping. https://ibm.github.io/mcp-context-forge/using/mcpgateway-translate/
- **Authentication:** JWT (HS256 or RS256/ECDSA; `JWT_AUDIENCE_VERIFICATION`, `JWT_ISSUER_VERIFICATION`, `REQUIRE_JTI`, revocation table — note "revocation and user lookups **fail open** during a database outage"). SSO via OIDC/OAuth2: GitHub, Google, IBM Security Verify, Entra ID, Keycloak, Okta, generic OIDC (`SSO_GENERIC_*`), with `team_mapping` and Keycloak realm/client role mapping. https://ibm.github.io/mcp-context-forge/manage/securing/ and .../manage/sso/
  - **RFC 9728 inbound:** serves `/.well-known/oauth-protected-resource/servers/{server_id}/mcp` with `authorization_servers` and returns 401 with `WWW-Authenticate: Bearer resource_metadata=...`; enabled per server via `oauth_enabled: true` + `oauth_config.authorization_servers`. Whether it validates tokens from that external AS via JWKS and binds audience per RFC 8707 is **not stated** on the page. https://ibm.github.io/mcp-context-forge/architecture/rfc9728-compliance/
  - **Upstream OAuth:** client-credentials and authorization-code (per-user tokens keyed by `app_user_email`, encrypted with `AUTH_ENCRYPTION_SECRET`, PKCE automatic) and **outbound DCR** (`MCPGATEWAY_DCR_ENABLED`, `MCPGATEWAY_DCR_ALLOWED_ISSUERS`, …). Token exchange / OBO to upstream: **not found**. https://ibm.github.io/mcp-context-forge/manage/oauth/ and .../manage/dcr/
- **Authorization:** RBAC with teams and roles; canonical permissions `tools.*`, `resources.*`, `admin.*`; `teams` JWT claim scoping; server-scoped and permission-scoped tokens; RBAC can hide tools/prompts/resources.
  - **External PDP hooks (the strongest among candidates):** Plugin framework hook points `prompt_pre_fetch`, `prompt_post_fetch`, `tool_pre_invoke`, `tool_post_invoke`, `resource_pre_fetch`, `resource_post_fetch`, `http_pre_request`, `http_auth_resolve_user`, `http_auth_check_permission`, `http_post_request`, `agent_pre_invoke`, `agent_post_invoke`. Payloads: `ToolPreInvokePayload{name, args, headers}`, `ToolPostInvokePayload{name, result}`. Modes `enforce`, `enforce_ignore_error`, `permissive`, `disabled`; external plugins run as separate services over MCP (STDIO/Streamable HTTP) or gRPC (`kind: external`). https://ibm.github.io/mcp-context-forge/using/plugins/
  - **OPA plugin** (`plugins/external/opa`, `OPAPluginFilter`): external MCP plugin server bundling an OPA server; hooks all six MCP hooks; config `opa_base_url: http://127.0.0.1:8181/v1/data/`, `applied_to.tools[].tool_name`, `extensions.policy`, `policy_endpoint(s)`, `policy_input_data_map`, `policy_modality`; Rego input is `payload.args` + `context`. https://raw.githubusercontent.com/IBM/mcp-context-forge/main/plugins/external/opa/README.md
  - **Cedar plugin** (`plugins/external/cedar`): `policy_lang: cedar|custom_dsl`, principal `Role::"..."`, resources `Server::`/`Agent::`/`Prompt::`/`Resource::`, post-hook output redaction via `policy_redaction_spec`. https://raw.githubusercontent.com/IBM/mcp-context-forge/main/plugins/external/cedar/README.md
  - No Envoy ext_authz/ext_proc.
- **Guardrails:** 50 catalogued plugins incl. PII Filter, Secrets Detection, Harmful Content Detector, Content Moderation (IBM Watson, Granite Guardian, OpenAI, Azure, AWS), LLMGuard (external), ClamAV Remote, URL Reputation, VirusTotal, SQL Sanitizer, Safe HTML, Schema Guard, Output Length Guard, Deny/Regex filters, Rate Limiter, Circuit Breaker, Watchdog, Webhook Notification, Vault. https://ibm.github.io/mcp-context-forge/using/plugins/plugins/
- **Observability:** `OTEL_ENABLE_OBSERVABILITY=true`, `OTEL_TRACES_EXPORTER=otlp`, `OTEL_EXPORTER_OTLP_ENDPOINT`; backends Phoenix, Jaeger, Tempo, Zipkin; Prometheus `GET /metrics/prometheus` (`ENABLE_METRICS`, JWT-protected). Span attribute content (tool args/results) is **not documented**; a "Tools Telemetry Exporter" plugin and `AuditLoggerPlugin` (`include_payloads`) exist. https://ibm.github.io/mcp-context-forge/manage/observability/
- **Deployment:** Helm chart `mcp-stack` (gateway + PostgreSQL + Redis, Ingress, NetworkPolicy); Docker Compose. **No operator or CRD.** Servers are registered via Admin UI or REST API (the chart ships example registration Jobs; strict SSRF defaults block private addresses → HTTP 422 until configured). https://ibm.github.io/mcp-context-forge/deployment/helm/
- **Tool scoping:** virtual servers bundling selected tools; RBAC hiding; gateway federation. Collision handling across federated servers: **not found**.
- **Security hardening:** does not run servers; no sandboxing, scanning or rug-pull detection found.
- **A2A:** "A2A (Agent-to-Agent) integration for external AI agents" plus `agent_pre_invoke/post_invoke` hooks (README).
- **Admin UI / health:** Admin UI; `/health`, `/ready`.

### 3. agentgateway (agentgateway.dev)
- **License:** Apache-2.0 (LICENSE verified). No feature gating found in the OSS docs (Solo.io sells commercial support; specifics **unverified**).

## Part C. Assessment against the stated enterprise requirements

Requirements: external OPA/Cedar policy decision point, OIDC, OpenTelemetry tracing, Kubernetes-native "deploy + configure" onboarding.

1. **agentgateway (data plane) + kmcp or ToolHive (runtime for stdio servers)** — best overall fit.
   - External PDP: Envoy-compatible `extAuthz` (works directly with OPA's Envoy plugin) at the HTTP layer, plus the MCP-aware ExtMCP gRPC guardrail hook that sees tool name, params and results and can mutate or deny per method/phase; CEL `mcpAuthorization` for in-proxy rules.
   - OIDC: `mcpAuthentication` implements the resource-server side of the MCP spec (PRM, 401 challenge, JWKS validation) with provider presets (Keycloak, Okta, Entra, Auth0…) and DCR proxying; upstream RFC 8693 / 7523 / OBO / ID-JAG exchange.
   - OTel traces/metrics/logs natively; tool args/results in access logs only (by design).
   - Kubernetes-native: Gateway API CRDs; "add a server" = one `AgentgatewayBackend` + `HTTPRoute`; Helm OCI charts; AAIF governance; tracks the 2026-07-28 spec.
   - Gaps: no stdio hosting in the K8s CRD (use kmcp `MCPServer` or ToolHive `MCPServer` to containerise npx/uvx servers), no server scanning or rug-pull detection, no built-in PII filter (add via ExtMCP or an LLM-route guardrail).

2. **ToolHive operator** — strongest *runtime* story with built-in policy.
   - Cedar is native and argument-aware (`arg_*`, annotations); `MCPWebhookConfig` gives an external validating/mutating PDP (payload schema undocumented — verify before relying on it for OPA); OIDC per server (`MCPOIDCConfig`), token exchange, embedded AS with DCR + CIMD; OTel spans carry sanitized tool arguments; 14 CRDs, Helm; Sigstore image verification; network isolation.
   - Gaps: no native OPA; IdP group→role mapping, console and centralized audit are Enterprise-only; 0.x near-daily releases; no A2A.

3. **IBM ContextForge** — richest policy/guardrail plugin surface, less cloud-native.
   - Native external OPA and Cedar plugins with `tool_pre_invoke`/`tool_post_invoke` payloads (name, args, result); 50 guardrail plugins; SSO (Keycloak/Okta/Entra/generic OIDC) and RFC 9728 PRM inbound; OTel OTLP and Prometheus; Helm chart.
   - Gaps: no operator/CRD (registration via UI/API or Jobs); stdio needs a hand-built `mcpgateway.translate` sidecar; Python monolith with Postgres/Redis; documented fail-open behaviours (revocation on DB outage) to review; span contents undocumented.

Honourable mentions: **Obot** if you want a governance product (UI, audit, Kubernetes hosting, webhook/MCP filters as an external PDP) and accept license-key gating and undocumented OTel; **Kuadrant mcp-gateway** if you are already on Istio/Authorino (early, no releases).
