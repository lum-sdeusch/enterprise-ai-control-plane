# Policies

One OPA bundle governs both enforcement points: the MCP tool path and the LLM path. The adapter
asks for a single document, `data.eacp.decision`, on every phase of every call.

## Layout

```
policies/
  .manifest                 bundle manifest; scripts/build-bundle.sh stamps the git revision
  eacp/config.json          hand-written policy configuration (thresholds, routing table, model names)
  eacp/manifests.json       GENERATED by scripts/compile-manifests.py from tools/, agents/, teams/
  rego/00-global/           global guardrails. Owned by security (CODEOWNERS)
  rego/10-teams/<team>/     team rules, package eacp.teampolicy.<team>
  rego/20-tools/<server>/   tool rules,  package eacp.toolpolicy.<server with - as _>
  rego/30-agents/<agent>/   agent rules, package eacp.agentpolicy.<agent with - as _>
  tests/fixtures/*.json     one input document per scenario, loaded at data.tests.fixtures.<name>
  tests/*_test.rego         unit tests; `make policy-test`
```

Layer packages only need to define `deny contains {"code": ..., "msg": ...}`. The global
aggregator picks them up by the team, server and agent in the input. A layer cannot grant what
a global rule denies; it can only add denials.

## Input contract (what the adapter sends)

```json
{
  "phase": "request | response | list | llm_route | llm_request | llm_response",
  "subject": {
    "sub": "alice", "groups": ["support"], "team": "support", "clearance": "restricted",
    "data_label": null,
    "act": {"client_id": "agent-support-assistant"}
  },
  "agent": "support-assistant",
  "tool": {"server": "customer-db", "name": "execute_sql"},
  "arguments": {"sql": "select ..."},
  "findings": {
    "pii": [{"type": "EMAIL_ADDRESS", "start": 10, "end": 28, "score": 0.99}],
    "secrets": [{"type": "aws_access_key_id", "start": 0, "end": 20}],
    "injection": {"score": 0.02, "label": "safe", "categories": []},
    "sensitivity": {"label": "internal", "confidence": 0.7}
  },
  "taint": {"touched_pii": false, "touched_restricted": false, "touched_untrusted_content": false},
  "pinning": {"tools": "sha256:..."},
  "approval": {"approved": false, "approver": null, "approver_groups": []},
  "llm": {"requested_model": "eacp-auto", "target_class": "external"},
  "conversation_id": "…", "trace_id": "…"
}
```

The adapter verifies tokens, approval records and pinned hashes before building the input; the
policy reasons about the verified facts. Findings come from the guardrail service and are
probabilistic; thresholds live in `eacp/config.json`, so changing a threshold is a reviewed
policy change, not a code change.

## Output contract (`data.eacp.decision`)

```json
{
  "allow": false,
  "reasons": [{"code": "exfil_after_restricted", "msg": "…"}],
  "redactions": [{"type": "EMAIL_ADDRESS", "start": 10, "end": 28, "score": 0.99}],
  "require_approval": {"approver_group": "support-approvers", "allow_self": false, "reason": "…"},
  "route_label": "restricted",
  "route_target": "eacp-inhouse",
  "taint_updates": {"touched_restricted": true},
  "audit_tags": ["phase:request", "tool:customer-db/execute_sql"],
  "policy_revision": "a1b2c3d"
}
```

`allow` is false whenever any reason exists or an approval is pending. `redactions` can be
non-empty on an allowed call; the adapter applies them before forwarding. `taint_updates` is only
non-empty on response phases. `route_label` and `route_target` are computed on every phase and
used by the LLM callout. `policy_revision` comes from the bundle manifest, so every audit record
can name the exact policy that produced it.

## tools/list

For `tools/list` the adapter queries `data.eacp.entitlement.visible_tools` once and filters the
listing to that set. The set is the intersection of group entitlement, the agent manifest,
the caller's clearance and the agent's classification ceiling.
